# Руководство пользователя: GUI, CLI, тесты

Эмулятор кассы «ЭТИМ» (AT89C55VD / MCS-51). Эта страница — практическое
руководство: как запустить окно кассы, как пользоваться мышью и клавиатурой,
все режимы командной строки, как читать вывод `--selftest`/`--headless` и
как запускать тесты. Архитектура — в [architecture.md](architecture.md),
контракт «плата ↔ интерфейс» — в [board_contract.md](board_contract.md).

На Windows перед запуском задайте UTF-8 (иначе кириллица в консоли и тестах
может отображаться кракозябрами):

```powershell
$env:PYTHONUTF8 = 1
```

Сторонние пакеты не нужны: только Python 3 с Tkinter (входит в стандартную
поставку). Проверка, что всё на месте: `python main.py --selftest`.

---

## 1. Быстрый старт

```bash
python main.py                    # окно кассы: demo51 (по умолчанию) — рабочие
                                  #   кнопки, индикатор и печать чека
python main.py --backend recovered  # настоящая прошивка ETIM: бут + самотест
                                  #   (клавиатура пока не опрашивается, §4.3)
python main.py --list             # список режимов и образов ПЗУ, без запуска
python main.py --selftest         # проверка модулей, без окна
python main.py --headless 5       # эмуляция 5 секунд без окна + печать статуса
python main.py --help             # все опции
```

### Все опции `main.py`

| Опция | Значение |
| --- | --- |
| `--backend`, `-b {recovered, etim, demo51}` | что запускать; по умолчанию `demo51` — рабочие кнопки/чек; `recovered` — настоящая прошивка ETIM, её клавиатурный цикл ещё не восстановлен (§4.3) |
| `--dump ПУТЬ` | путь к `.c`-дампу декомпиляции (для `recovered`); по умолчанию — `docs/nm27c512n_decompiled.c` |
| `--self-test` | плата сама показывает картинку на индикаторе и печатает образцовый чек (работает для `etim`/`demo51`, для `recovered` игнорируется) |
| `--headless СЕК` | без окна: гонять эмуляцию N секунд и напечатать статус |
| `--list` | показать варианты `--backend` и образы прошивок, выйти |
| `--selftest` | быстрая проверка, что все модули грузятся (без окна) |
| `-h`, `--help` | справка |

Коды выхода:

| Код | Когда |
| --- | --- |
| `0` | успех (`--list`, `--selftest` без ошибок, `--headless` без ошибок эмуляции, нормальное закрытие GUI) |
| `1` | `--selftest` нашёл сломанный модуль **или** `--headless` завершился с ошибками эмуляции |
| `2` | не удалось поднять выбранный бэкенд, либо не открылось корневое окно Tk |

> Не путайте `--selftest` и `--self-test` (через дефис): первое — проверка
> импорта модулей, второе — самотест платы.

## 2. Режимы эмуляции (бэкенды)

Список всегда можно получить вживую: `python main.py --list`.

```
Варианты запуска (--backend):
  recovered  восстановленный декомпилированный код (recover/)
  etim       эмулятор 8051 + дамп nm27c512n.hex
  demo51     демонстрационная 8051-программа (стенд-ин)

Образы прошивок в firmware/:
  nm27c512n.hex
```

* **`recovered`** — исполнение восстановленного из декомпилирования кода
  (`recover/`: парсер → AST → интерполятор → HAL), а поверх — **оригинальных
  байтов прошивки на ядре `m8051`** (`recover/realrun.py`). После rebasing
  вектор сброса настоящий: запись `0x8000` = CPU `0x0000` — `LJMP 0x0A06`,
  цель внутри дампа, поэтому байты стартуют «сами», таймеры прошивки сами
  диспетчеризуют её обработчики (мультиплексор дисплея CPU `0x02D9`);
  недостающая верхняя половина CPU `0x8000..0xFFFF` названа в поле `reason`
  и честно останавливает CPU, если до неё дойдёт дело.
* **`etim`** — настоящее ядро 8051 на байтах `firmware/nm27c512n.hex` после
  rebasing: образ занимает CPU `0x0000..0x7FFF` и крутится от настоящего
  вектора сброса; верхняя половина `0x8000..0xFFFF` в дамп не вошла
  (`missing_bytes: 32768`).
* **`demo51`** — демонстрационная программа `firmware/demo/cashier.asm`,
  собранная ассемблером `tools/asm51.py`: настоящий машинный код 8051 на той
  же плате кассы. Это **стенд-ин, а не оригинальная прошивка** — в строке
  состояния это всегда видно.

Общая схема: выбранный бэкенд владеет объектами `display` / `keyboard` /
`printer`, фоновый поток раз в 20 мс дозирует ему машинные циклы
(1 МГц при кварце 12 МГц), а окно Tk перерисовывается каждые 50 мс.

## 3. Интерфейс кассы (GUI)

Окно запускается командой `python main.py` (плюс нужный `--backend`).
Состав окна сверху вниз:

1. **Шапка** — название, строка об АО «ЭТИМ» и процессоре, список режимов
   индикатора.
2. **Индикатор кассы** — крупные зелёные цифры на чёрном. Размер
   переключается списком «ИНДИКАТОР» (как в меню, точные подписи):
   `20 x 1  (касса)`, `20 x 2  (касса, 2 строки)`, `16 x 1  (ценник)`,
   `8 x 1   (табло)`, `40 x 1  (широкий)`. Пока режим не выбран
   вручную, индикатор автоматически следует за реальной геометрией платы
   (у настоящей платы 8×1, у моковой — 20×2); после ручного выбора
   автоследование отключается.
3. **Клавиатура** — раскладка объёмных кнопок строится по списку
   `keyboard.keys` платы: цифровой блок `7 8 9 / 4 5 6 / 1 2 3 / 0 00 .`,
   правая колонка `СУММА ОПЛ X ИТОГ ВВОД СБРОС ОТМЕНА`, служебный ряд
   `КАССИР СЕРВИС РЕЖИМ ЧЕК КС Z ПИТ` и ряд навигации
   `◀ ▶ ПРОБЕЛ ТАБ`. Цвета: цифры — жёлтые, арифметика — синие,
   служебные — зелёные, `СБРОС`/`ОТМЕНА` — красные, печать — оранжевые.
   Все **33 клавиши** помещаются в окно: раскладка перекомпонована под
   пропорцию 4:3, окно подгоняется под содержимое автоматически
   (замер на стандартном десктопе — 1132×693).
4. **Чек** — «бумажная лента» справа от клавиатуры (см. §3.3).
5. **Строка состояния** — статус платы, ошибки, счётчики (см. §3.4).
6. **Меню** — `Касса`, `Вид`, `Справка` (см. §3.5).

### 3.1 Работа мышью

* Клик по любой кнопке клавиатуры = одно нажатие клавиши кассы
  (`keyboard.tap(name)`); на время удержания кнопка визуально «вдавливается»
  (`relief=SUNKEN`), при отпускании возвращается.
* Кнопки панели чека: `ПИТ ↓` — подать одну строку бумаги
  (`printer.feed(1)`), `Очистить` — очистить ленту (`printer.clear()`).
* Потеря фокуса окном возвращает все кнопки в выпуклое состояние.

### 3.2 Работа с физической клавиатуры

Клавиши нажимаются и отпускаются как на настоящей кассе
(`<KeyPress>` → `press`, `<KeyRelease>` → `release`). Привязка применяется
только если такая клавиша есть в раскладке платы.

| Клавиша ПК | Клавиша кассы |
| --- | --- |
| `0`–`9` | цифры `0`–`9` |
| `.` или `,` | `.` |
| `Enter` / `Enter` на цифровом блоке (`KP_Enter`) | `ВВОД` |
| `Esc` | `СБРОС` (или `ОТМЕНА`, если `СБРОС` нет) |
| `Backspace` | `СБРОС` |
| `Delete` | `ОТМЕНА` |
| `←` / `→` | `СТРЕЛКА_ВЛЕВО` / `СТРЕЛКА_ВПРАВО` |
| `Пробел` | `ПРОБЕЛ` |
| `Tab` | `ТАБ` |
| `F1` | `КАССИР` |
| `F2` | `СЕРВИС` |
| `F3` | `РЕЖИМ` |
| `F4` | `ЧЕК` |
| `F6` | `Z` (Z-отчёт) |
| `F7` | `ПИТ` (подача бумаги) |
| `F8` | `КС` (X-отчёт) |

`F5` не относится к клавишам кассы — это «Обновить экран» (меню `Касса` и
привязка в `ui/app.py`). Прочие сочетания: `Ctrl+Q` — выход, закрытие
крестика — тоже выход.

### 3.3 Чек (бумажная лента)

* Лента рисуется из `printer.paper()` (по контракту — список строк сверху
  вниз); сверху UI добавляет типографскую шапку `АО "ЭТИМ" Спб`.
* Автопрокрутка вниз, пока вы не открутили вручную; горизонтальная
  прокрутка — если строка длиннее ленты.
* Кнопка `ПИТ ↓` подаёт бумагу (`feed(1)`), `Очистить` вызывает
  `printer.clear()` (там же это делает меню `Касса → Очистить чек`).
* Индикатор-«лампочка» справа от кнопок: горит, пока `printer.is_busy()`
  (принтер занят), гаснет — готов.
* Напечатанное появляется только тогда, когда прошивка реально шлёт байты в
  принтер; в режиме `--self-test` плата печатает образцовый чек сама
  (`КАССА`, `1 Х 12.34 12.34`, `ИТОГ 12.34`, `СПАСИБО!` и т. п.).

### 3.4 Строка состояния

Слева направо (пустые части пропускаются):

* `source` и `reason` из `board.status()` — какой бэкенд работает и почему
  он остановился/остановлен (`recovered`, `demo`, `self-test`, причина
  остановки ядра и т. п.);
* `ОШИБКА: ...` — если отрисовка экрана/чека упала (на самом индикаторе в
  этом случае пишется `ОШИБКА ЭКРАНА`);
* `клавиш: N` — сколько кнопок построено, `последняя: X` — последняя
  нажатая;
* `принтер: готов/занят/н/д`;
* `экран: C x L` — фактическая геометрия индикатора.

Справа — счётчик `цикл N` (число обновлений интерфейса, раз в 50 мс).

### 3.5 Меню

* **Касса** — `Обновить экран F5`, `Очистить чек`, `Выход`.
* **Вид** — `Только экран` / `Экран и чек` (прячет/показывает панель ленты).
* **Справка** — `О программе` (окно с краткими сведениями).

## 4. Режимы командной строки без окна

### 4.1 `--list`

`python main.py --list` печатает варианты `--backend` и найденные образы
прошивок в `firmware/` (см. §2), код выхода `0`. Удобно для быстрой проверки,
что проект видит свои `.hex`-файлы.

### 4.2 `--selftest` — проверка, что всё грузится

`python main.py --selftest` импортирует ключевые модули и, отдельно,
создаёт/разрушает окно Tk. **Окно кассы при этом не открывается.**

Нормальный вывод (код выхода `0`):

```
  ok    m8051
  ok    disasm
  ok    recover.parse
  ok    recover.interp
  ok    board.cashboard
  ok    ui.app
  ok    recover.session
  ok    tkinter (окно создаётся)
```

Как интерпретировать:

| Строка | Значение | Влияет на код выхода |
| --- | --- | --- |
| `ok    <модуль>` | модуль импортируется без ошибок | — |
| `FAIL  <модуль>: <Тип>: <текст>` | модуль сломан (обычно опечатка/зависимость) | да → код `1` |
| `ok    tkinter (окно создаётся)` | графическое окружение доступно, GUI-режим возможен | — |
| `warn  tkinter: <текст> (графический режим недоступен)` | Tk есть, но дисплей/окно не создать (например, SSH без X) | **нет**, код остаётся `0`, если модули в порядке |

То есть `warn tkinter` не ломает проверку — он лишь говорит, что запускать
GUI в этом окружении не выйдет (используйте `--headless`).

**Финальные факты о экране (после PPI-эксперимента).** При дефолтной
проводке `WIRING: PPI_BASE=0x0000` (страница ППИ — всё ещё гипотеза:
известно, что в этом месте она неверна, но настоящая страница пока не
найдена) декод 8255 попадает внутрь диапазона собственного самотеста
внешней RAM прошивки: при загрузке прошивка прогоняет по XDATA
`0x0000..0x1FFF` четыре тестовых паттерна и «walking test» (256 блоков),
и самое первое сравнение падает — порт A отдаёт `0xFF` вместо `0x00`.
Прошивка уходит в свою штатную ветку ошибки и показывает **свой
собственный экран самодиагностики**. Свежий прогон
`python main.py --backend recovered --headless 15` (снят вживую; поля
`consumer`/`reason` — те же, что в полном блоке 3 с выше, здесь сокращены):

```

--- статус ---
  ...
  cpu_instructions: 1099825
  display:   .h0000
  entry: 0x0A06
  entry_covered: True
  ...
  halted: False
  mux_calls: 723
  real_hex: True
  reason: reset vector record 0x8000 = LJMP 0x0A06; ... ; NOT dumped: the upper half 0x8000..0xFFFF of CPU space - execution halts honestly if it ever fetches there; consumer: ...
  running: True
  source: recovered
  steps: 723
  кадров эмуляции: 82, ошибок: 0
  экран: '  .h0000'
  чек: 0 строк
```

`'  .h0000'` — это адрес упавшей ячейки: `0000h` (цифры — nibble-шрифт
из RAM самой прошивки, символ `h` записан литерой, байт `0x74`), плюс
пробелы и точка-разделитель. После падения ядро паркуется на CPU `0x1F60`
(`SJMP $`), а развёртку продолжает крутить таймер 0 (`mux_calls: 723`) —
поэтому экран выглядит «живым». Это **настоящий вывод настоящей
прошивки** (честная самодиагностика), а не сбой эмуляции; диагностика —
`tools/_diag_base0.py`.

### Восстановление загрузки настоящей прошивки (текущее состояние)

Дефолтную проводку `PPI_BASE=0x0000` не меняли — `--backend recovered` в
обычном запуске по-прежнему честно показывает самотест ошибки (см. выше).
Однако ниже пройден путь, на котором настоящая прошивка загружается
дальше. Все пункты доказаны исполнением её настоящих байтов и
воспроизводятся одной командой:

```
python tools/_diag_real_boot.py
```

Найденная проводка собрана в `board/cashboard.py::RECOVERED_WIRING`
(ППИ вне диапазона ОЗУ; включены «полевые» устройства-ответчики). Регрессия —
`tests/test_recover.py::TestRestoredBoot` (самотест пройден, загрузка до
главного цикла, прошивка сама сканирует матрицу, коды ложатся в кольцо).

Найденная цепочка:

1. **ППИ вне диапазона самотеста.** При `PPI_BASE=0xF000` (и
   `PPI_MIRROR_BASES=()`) XDATA `0x0000..0x1FFF` — чистая RAM, самотест
   прошивки проходит (`walking test` читает записанное). Реальная страница
   ППИ пока неизвестна (HYPOTHESIS `0xF000`), но внутри диапазона самотеста
   её быть не может — иначе самотест падал бы и на настоящей машине.
2. **INT0 в режиме уровня.** Прошивка использует `SETB TCON.1` как
   программную пометку; на настоящем кремнии в режиме уровня (`IT0=0`)
   флагом владеет железо (сэмплирование линии), поэтому прерывание не
   взводится. Ядро `m8051` теперь это воспроизводит
   (`cpu.py::_poll_interrupts`): программный `IE0` в режиме уровня не
   создаёт прерываний, программный `IE0` в режиме границы (`IT0=1`)
   работает как классический software-interrupt. Это устранило раннее
   «выключение» кассы (обработчик `0x04D1`).
3. **Устройства-ответчики загрузки.** Два места ждут ответа от железа —
   без них прошивка уходит в ветку ожидания:
   * страница `0x80`: код `0x4CE0`/`0x51E7`/`0x51F4` читает три раза и
     ждёт последовательность `00 → 55 → AA`;
   * XDATA `0x933E`/`0x933F`: код `0x07D7` ждёт пару `55 AA`.
   В диагностике это моделируется как устройство-ответчик; на реальной
   плате это, видимо, поле/контроллер со своим протоколом (открытая
   электрическая находка).
4. **Прескан клавиатуры.** Код `0x0A7E` читает `0x9100+i` (строки 0..7):
   `0` = в строке нет нажатых, `!=0` = есть контакт. Пустая машина обязана
   вернуть `0x00`, иначе прошивка уходит в спец-режим и паркуется в
   `0x1F60` (проверено трассировкой).
5. **Скан клавиатуры.** Внутри ISR таймера 0 (`0x02D9`) прошивка читает
   `0x9130+row`, инвертирует (`CPL A`), держит антидребезг по слоту
   `0x30+row` и при изменении кладёт код `row<<3 | col` в кольцо
   XDATA `0x0C80` (указатели IRAM `0x4E/0x4F`). Семантика чтения —
   **активная-ВЫСОКАЯ маска нажатий** (покой `0x00`, нажатие = бит
   колонки): при активном-LOW ворота постановки в кольцо (`0x03AB-0x03C1`)
   не проходят никогда. Колонки стробируются линией выбора знакоместа
   (`0xA2`): вне диапазона знакомест (сетки `8..13`) строка читается
   нулём — на этом пути код `0x0434` выставляет сервисные флаги ряда 7.
6. **Главный цикл.** Прошивка доходит до цикла `0x06A4` (опрос кольца),
   читает коды и реагирует на служебную клавишу «1» (`0x10`), рисуя на
   индикаторе `'  . X0 C'`. Нажатия сканируются ЕЮ САМОЙ и попадают в
   кольцо: `5 → 0x09`, `СУММА → 0x04`, `0 → 0x18`, «1» → `0x10`.

### Где проходит граница восстановления

Отдельные находки о том, что ещё предстоит и чего в дампе нет:

* **Цепочка входа в рабочий режим найдена (следующий этап).** Все адреса —
  CPU, байты присутствуют:

  1. `0x4937..0x4957` — инициализация рабочего режима:
     `SETB 20h.7; CLR 21h.0; CLR 21h.1; MOV 42h,#28h; MOV 43h,#FAh;
     MOV 44h,#00h; SETB 26h.1; CLR 26h.2; CLR 26h.3;
     MOV TL0,#0CCh; MOV TH0,#0F8h; MOV 1Fh,#00h; SETB EX0`;
     перед ней (`0x491E..0x4932`) — ожидание кода `0x1E`/`0x20` и флаг
     `27h.7`.
  2. `LJMP 0x0C6A` → `LCALL 5931/5B1F/1C41/1C34; SETB 20h.1;
     LJMP 0x2084` → `0x20B5: LJMP 0x0C81`.
  3. `0x0C81` — **главный рабочий цикл**: `LCALL 5C98` (чтение кольца),
     проверки `26h.1/26h.2/26h.3`, `25h.4`, переходы `0x0BC0`/`0x61A1`.
     Принудительный вход в `0x0C81` (диагностический прыжок) реально
     оживляет запись в принтер — наблюдались сырые байты `1F 05 03 01`;
     значит цикл рабочий, но требует согласованного состояния ОЗУ, которое
     создаёт предыдущая цепочка.
  4. **Timer-1 запускается** в `0x5AD5..0x5AF3`: `JNB 21h.1,5AE5` →
     `SETB 23h.3; CLR 24h.0; LCALL 5AE5` (`MOV TMOD,#11h;
     ORL TCON,#C0h` = TR0|TR1; `SETB EX1; SETB EA`). Гейт — бит `21h.1`,
     который ставится в ISR (`0x049A`) при исчерпании **скрипта событий**.
  5. **Скрипт событий в ISR.** В прерывании таймера-0 (`0x046F..0x04C5`)
     работает движок: таблица пар «длительность/код» по `0x495A`, счётчики
     IRAM `0x42`/`0x43`/`0x44`; коды кладутся в то же кольцо `0x0C80`
     (`0x4BF..0x4C5`), а по достижении индекса `0x44 == 0x78` ставится
     `21h.1` — то есть машина «проигрывает» стартовую последовательность
     как нажатия, затем включает рабочий режим. В нашем прогоне движок
     стоит (`0x44=0x43=0x42=0xFF`), потому что не достигнута его ветка
     (`20h.7`), — именно её и требует пункт 1.
* **Вектор Timer-1 указывает ВНУТРЬ дампа.** Байты вектора `0x001B` =
  `C0 E0 C0 D0 02 00 C1` (`PUSH ACC; PUSH PSW; LJMP 0x00C1`) — обработчик
  лежит по CPU `0x00C1` и целиком присутствует; дальше он уходит в
  `0x0135` (крупная функция обновления/сканирования).
* **Косвенные вызовы.** В декомпиляции видно вычисляемые переходы через
  `DAT_EXTMEM_1b83` (`*(code *)((ushort)DAT_EXTMEM_1b83 + 0x1b83)(…)`,
  см. `docs/hardware_evidence.md`) — таблица кода в XDATA; такие вызовы
  тоже могут вести в отсутствующую половину, поэтому статическая картина
  вызовов неполна.
* **Флаги «батарейного» ОЗУ.** Прошивка различает холодный и тёплый старт
  по XDATA `0x00D1` (читается в `0x05B0`/`0x0698`, пишется в `0x0A48`) и
  по XDATA `0x00FD` (энергонезависимое состояние, используется в `0x05ED`);
  наша модель начинает с нулевого ОЗУ, поэтому всегда идёт «холодным»
  путём — на настоящей кассе с заряженной батареей состояние могло быть
  другим.
* **Устройство на странице `0x93`.** Помимо пары `55 AA` в
  `0x933E/0x933F` прошивка читает `0x930A` (бит 7 = занято, опрос с
  таймаутом по `0x4C`) и записи в `0x9310+` (16-битный указатель
  `0x9310/0x9311`) — это отдельное «полевое» устройство с протоколом;
  электрическая реализация пока HYPOTHESIS.
* **Раскладка клавиатуры.** В `firmware/demo/cashier.asm` верхний
  комментарий фиксирует «раскладку матрицы, согласованную с hal-ppi»
  (столбцы 3..7: СБРОС/ВОЗВРАТ/СКИДКА/КС/Z, СУММА/КАССИР/СЕРВИС/X/ЧЕК,
  ОПЛ/РЕЖИМ/ВВОД/ПИТ/ТАБ, ИТОГ/ПОДЫТОГ/ОТМЕНА/ПРОБЕЛ/◀), а координаты,
  которые реально отдаёт `board/keyboard.py`, — упрощённый стенд-ин.
  Настоящая физическая раскладка требует сверки с документацией кассы;
  цифры и коды `row<<3|col` при этом совпадают.

Что пока **не** восстановлено:

* полный сценарий «продажа» упирается в сервисные ворота `0x06A4`:
  коды `0x1B/0x0A/0x28` + флаги `26h.3`, `25h.7`, `20h.2/20h.3/20h.4`
  (открытая находка — что именно должно переключить эти состояния);
* верхняя половина ПЗУ `0x8000..0xFFFF` физически отсутствует в дампе —
  часть обработчиков (в первую очередь Timer-1, см. выше) живёт там;
  обращения туда честно останавливают CPU;
* интерактивный сценарий «продажа» для пользователя по-прежнему даёт
  стенд-ин `--backend demo51` — он работает целиком.

Поля блока `--- статус ---` (состав зависит от бэкенда):

| Поле | Что это |
| --- | --- |
| `source` | какой бэкенд отвечает за статус (`demo`, `etim`…) |
| `cycles` / `ops` / `pc` | машинные циклы, исполненные опкоды, текущий счётчик команд |
| `halted` / `reason` | остановилось ли ядро и почему (например, честный останов на fetch в отсутствующую верхнюю половину CPU `0x8000..0xFFFF`) |
| `entry` / `entry_covered` | адрес вектора сброса, прочитанный из образа (`0x0A06`), и покрыт ли он дампом (после rebasing — всегда `True`) |
| `missing_pc` / `missing_bytes` | какого адреса коснулся недостающий байт и сколько байтов CPU-пространства не покрыто дампом (для `etim`: `32768`, `missing_pc: None` = ни разу не понадобилось) |
| `real_hex` / `isr_calls` / `mux_calls` / `cpu_instructions` | исполняются ли оригинальные байты (`recovered`), сколько раз сработали обработчики прошивки и сколько инструкций выполнило ядро |
| `consumer` | вердикт, кто наполняет буфер дисплея (`producers RUN` = настоящий главный цикл прошивки) |
| `functions_loaded` / `functions_failed` / `globals` | статистика разбора декомпилированного дампа |
| `receipt_lines` | строк в принтере |
| `кадров эмуляции` | сколько раз дозированы циклы (штатно ~50 в секунду; меньше, если эмуляция не успевает за реальным временем) |
| `ошибок` | исключения фонового потока; первые до 5 печитаются с префиксом `!` |
| `экран` | `display.text()` — ровно `columns*lines` символов |
| `чек: N строк` | длина ленты и последние до 8 строк с префиксом `|` |

### 4.4 `--self-test` — самотест платы

`python main.py --backend demo51 --self-test --headless 3` заставляет плату
прогнать себя через настоящие порты (`ext_write`, тот же путь, что у
процессора): сначала зажечь цифры `12345678` на индикаторе, затем напечатать
образцовый чек (и дальше обычный код бэкенда продолжает работать поверх).
Ничего не подделывается «напрямую» в `display`/`printer` — только записи
в порты ППИ. Факт самотеста виден по ленте — печатаются ровно 7 строк:

```
  чек: 7 строк
    | КАССА
    | --------------------
    | 1 Х 12.34      12.34
    | ИТОГ           12.34
    | СКИДКА 0%  БЕЗНАЛИчН
    | --------------------
    | СПАСИБО!
```

(Последняя «Ч» читается строчной: в шрифте эмулируемого принтера для «ч»
нет отдельного заглавного байта — см. `ENCODE_BACK` в `board/printer.py`.)

Поле `source` в блоке статуса при этом остаётся от бэкенда (`demo`, `etim`) —
«self-test» ставится внутри `board.status()`, а `--headless` печатает статус
бэкенда.

`.c`-файл декомпиляции вместо `docs/nm27c512n_decompiled.c`.

### Как интерпретировать вывод

Успешный прогон:

```
----------------------------------------------------------------------
Ran 421 tests in 296.2s

OK
```

Прогон с падениями (схема, конкретные имена и цифры любые):

```
FAIL: test_key_press_changes_the_display (test_demo_firmware.TestDemoOnMockBus.test_key_press_changes_the_display)
AssertionError: 'ДЕМО-ПРОГРАММА' not found in '...'
----------------------------------------------------------------------
Ran N tests in NN.Ns

FAILED (failures=N)
```

* `FAIL: <тест>` — упал `assert` (`AssertionError`); строки ниже — сам traceback
  (класс, метод, ожидаемое/фактическое значение).
* `ERROR: <тест>` — исключение вне `assert` (чаще всего проблема setup/teardown).
* Строка `Ran N tests` — фактическое число выполненных тестов; `OK` / `FAILED (failures=N)`
  — итог; код выхода `0` / `1` соответственно.
* Тихий режим `-q` скрывает зелёные тесты и оставляет только падения —
  искать удобнее всего по `FAIL:`/`ERROR:`.
* `tests/test_ui_headless.py` не открывает окон: тесты UI идут и в
  бездисплейном окружении.
* `OK (skipped=N)` — все зелёные, но сработали условные пропуски: это
  skip-guard'ы известных пробелов, задокументированы в самих тестах
  (`test_cpu_conformance`, `test_opcodes`, `test_perf`), либо в окружении
  нет Tk/платы. В контрольном прогоне `N = 0`.

## 6. Инструменты (`tools/`)

Все с `--help`; ниже — только самое нужное.

```bash
# отчёт по декомпиляции: итоги, таблица функций, непокрытые вызовы
python -m tools.recover_firmware report [-v]

# выдать восстановленные C и Python-реконструкции в каталог
python -m tools.recover_firmware emit [--out ДИР]

# исполнить одну восстановленную функцию
python -m tools.recover_firmware run FUN_CODE_810f [--args 1,2] [--steps 200000] [--trace]

# проверка инвариантов парсера/интерпретатора/эмиттера (14 ok + "selftest passed")
python -m tools.recover_firmware selftest

# анализ образа ПЗУ: векторы, дизассемблирование, трассировка, гистограмма
python -m tools.inspect_rom vectors
python -m tools.inspect_rom disasm [START] [COUNT]
python -m tools.inspect_rom trace [--cycles N] [--events]
python -m tools.inspect_rom histogram [--cycles N]

# ассемблер MCS-51 (собирает firmware/demo/cashier.asm)
python -m tools.asm51 firmware/demo/cashier.asm -o out.hex [--bin out.bin] [--org 0] [--listing]
```

`tools/disasm.py` — библиотека дизассемблера (CLI у неё нет), её используют
`inspect_rom` и тесты.
