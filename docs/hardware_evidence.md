# Доказательства по периферии кассы, извлечённые из декомпилированного кода

> **Источник истины — только `docs/nm27c512n_decompiled.c`** (псевдо-C Ghidra).
> Дополнительно, **как кросс-проверка**, используются байты
> `firmware/nm27c512n.hex` (файл проекта). Никаких внешних источников и догадок
> «как бывает у касс» — каждое утверждение либо подтверждено цитатой из дампа,
> либо помечено **HYPOTHESIS**.
>
> Обозначения:
> * `Lnnn` — строка файла `docs/nm27c512n_decompiled.c`;
> * `FUN_CODE_xxxx` — функция дампа; `stub` = в теле есть `halt_baddata()`;
> * `ROM 0xNNNN` — адрес в `firmware/nm27c512n.hex`;
> * **CONFIRMED** — прямая цитата из кода; **HYPOTHESIS** — вывод, следующий из
>   цитат неоднозначно.

Документ дополняет `docs/hardware_from_pseudocode.md` (там разбор по блокам) и
`docs/firmware_recovery.md` (там конвейер и статистика); здесь — **справочник
доказательств**: адрес → функция → строка.

## 0. Метод: как код обращается к железу

Три адресных пространства, различаемые по префиксам имён в дампе
(`recover/namespace.py`):

| Пространство | Имя в дампе | Пример |
| --- | --- | --- |
| SFR (прямая адресация) | имя регистра | `TCON`, `TL1`, `CMOD`, `P1` |
| Битовое | `XX.Y` в объявлении, `_N_M` в теле | `undefined P1.3;` ↔ `P1_3`, `undefined 22.1;` ↔ `_2_1` |
| Внутренняя RAM | `DAT_INTMEM_xx` | `DAT_INTMEM_3e` |
| Внешняя память (MOVX) | `DAT_EXTMEM_xxxx` и `CONCAT11(page, off)` | `DAT_EXTMEM_000b`, `CONCAT11(0xa1, param_2)` |

**Важно про внешнюю память.** Дамп называет ячейки внешней памяти **только
младшим байтом**: `DAT_EXTMEM_000b` — это `0x??0B`. Старший байт задаётся
отдельной записью в `P2`:

```c
L905:   P2 = 1;                 // FUN_CODE_b274 — старший байт адреса
L906:   DAT_EXTMEM_0015 = (undefined1)((ushort)(sVar3 + 1) >> 8);
L907:   DAT_EXTMEM_0016 = (undefined1)(sVar3 + 1);
```
(`P2` встречается **54 раза**: `L905/921/924/930` в `FUN_CODE_b274`,
`L1023/1039/1042/1048` в `FUN_CODE_b282`, `L1205/1221/1224/1230` в
`FUN_CODE_b469`, `L1470` в `FUN_CODE_ba2a`, `L1975/1993/2039/2083/2104…` в
заглушке `thunk_FUN_CODE_d398`, `L5054/5276/5645…` = `0xD1` в серии `FUN_CODE_f*`.)

Поэтому таблица ниже перечисляет **смещения**, а страницу (`P2` либо
`MOV DPH,#NN`) следует читать рядом с цитатой. Это же зафиксировано в
`recover/hal.py:144-146`.

| --- | --- | --- | --- | --- |

| `0x000B` | запись | `= 0x89` (×4) и `= 0xa9` (×4), условие `_7_4` | `FUN_CODE_b274` **L850, L852**; `FUN_CODE_b282` **L968, L970**; `FUN_CODE_b469` **L1138, L1140, L1153, L1155** | CONFIRMED |
| `0x0015` | запись | старший байт 16-битного регистра: `(ushort)(sVar3+1) >> 8` | `FUN_CODE_b274` **L906**; `FUN_CODE_b282` **L1024**; `FUN_CODE_b469` **L1206** | CONFIRMED |

| `0x0093` | запись | всегда `0` | `FUN_CODE_b274` **L934**; `FUN_CODE_b282` **L1052**; `FUN_CODE_b469` **L1234** | CONFIRMED |

| `0x00FF` | запись | второй байт пары: `puVar13[1] = 0x5a` | `thunk_FUN_CODE_d398` **L2307** | CONFIRMED |
| `0x0107` | запись | `= 0xFF` (инициализация, далее только чтение) | `FUN_CODE_ba2a` **L1461** | CONFIRMED |

| `0x0C7B` | rw | соседний байт пары: `pbVar10 = param_1 + 1; if (*pbVar10 != 0x5a) break;` — после `param_1 = &DAT_EXTMEM_0c7a` (L1950/L2765) это адрес `0x0C7B` | `thunk_FUN_CODE_d398` **L1946–1949**; `FUN_CODE_d398` **L2761–2764**; в `FUN_CODE_d381` **L2356–2361** та же операция идёт от `&DAT_EXTMEM_00fe` и даёт `0x00FF` | CONFIRMED как «второй байт пары `0x5A`»; какой именно адрес получится, зависит от `param_1` — **HYPOTHESIS** |
| `0x1B83` | rw | **не железо**: `DAT_EXTMEM_1b83 = …;` и `*(code *)((ushort)DAT_EXTMEM_1b83 + 0x1b83)(…)` — индекс в таблицу кода | `FUN_CODE_e818` **L3373**; `thunk_FUN_CODE_ea4f` **L3560, L3563**; `FUN_CODE_ea4f` **L3798, L3801** | CONFIRMED как программная переменная; в `hal.py` намеренно **не** помечена устройством |

> Замечание к `0x00FE`: запись идёт **косвенно** через указатель
> (`*puVar13 = 0xa5`), поэтому подсчёт обращений только по имени
> `DAT_EXTMEM_00fe` её не видит и ячейка выглядит «только на чтение». Цитаты
> выше показывают обратное.

### 1.1 Окна `CONCAT11(page, offset)` — страницы устройств

`CONCAT11(0xa1, x)` = 16-битный адрес `0xA100 | x`. В дампе встречаются ровно
три старших байта: `0xa1` (17 раз), `0xa2` (3), `0x81` (2).

| Окно | Что подтверждает дамп | Функции и строки | Статус |
| --- | --- | --- | --- |
| **`0xA1xx`** | запись байта в ячейку: `*(undefined1 *)CONCAT11(0xa1,param_2) = param_1;`; чтение байта с маской `& 0x80`; read-modify-write через `& 0xff80` | `FUN_CODE_810f` **L378–379**; `FUN_CODE_8135` **L461, L482, L520**; `FUN_CODE_822c` **L612**; `thunk_FUN_CODE_d398` **L2082, L2158, L2204**; `FUN_CODE_d381` **L2491, L2567, L2613**; `FUN_CODE_d398` **L2897, L2973, L3019** | CONFIRMED: окно ячеек дисплея (см. §2) |
| **`0xA2xx`** | `pcVar12 = (char *)CONCAT11(0xa2,uVar8); *pcVar12 = cVar7;` | `thunk_FUN_CODE_d398` **L2038–2044**; `FUN_CODE_d381` **L2447**; `FUN_CODE_d398` **L2853** | CONFIRMED: окно существует и пишется; **роль — HYPOTHESIS** (в паре с `0xA1xx`) |
| **`0x81xx`** | только **запись**, никогда не читается: `*pbVar4 = 0;` и `bVar3 = 0x55; *pbVar4 = bVar3;` | `FUN_CODE_8135` **L398–399** (запись 0), **L499–500** (запись `0x55`), **L501–502** (`T0 = 1; _2_7 = 1;`) | CONFIRMED write-only латч; назначение (принтер/строб) — HYPOTHESIS |
| **`0x69xx`** | `pbVar4 = (byte *)CONCAT11(param_6 + 'i', 0x31); bVar3 = pbVar4[param_5];` — чтение таблицы | `FUN_CODE_8135` **L509–511** | CONFIRMED: таблица в **коде** (кросс-проверка `ROM 0x81E7: MOV DPL,#31h / MOV A,#69h / ADD A,R6 / MOV DPH,A / MOV A,R5 / MOVC A,@A+DPTR`); сама половина ПЗУ отсутствует |

## 2. Дисплей

### 2.1 Запись в знакоместо — главный свидетель

`FUN_CODE_810f` (**L375–381**) — самая низкоуровневая операция вывода:

```c
void FUN_CODE_810f(undefined1 param_1, undefined1 param_2)   // L375
{
  *(undefined1 *)CONCAT11(0xa1,param_2) = param_1;            // L378
  FUN_CODE_83f0(CONCAT11(0xa1,DAT_INTMEM_3e));                // L379
}
```

* **CONFIRMED**: `param_2` — младший байт адреса, т.е. **номер знакоместа**;
  `param_1` — байт, который уходит в железо.
* Кросс-проверка байтами: `ROM 0x810F: MOV DPH,#A1h / 0x8112 MOVX @DPTR,A /
  0x8113 MOV DPL,3Eh / 0x8116 AJMP 83F0h` — совпадает строка в строку.

### 2.2 Восемь знакомест, циклическая нумерация 0..7

Прямые цитаты из `FUN_CODE_8135` (обёртка «+1 → 0» и «−1 → 7»):

```c
L410-413:  param_3 = param_3 + '\x01'; if (param_3 == '\b') param_3 = '\0';
L416-419:  param_3 = param_3 + -1;     if (param_3 == -1)   param_3 = '\a';
L449-452:  (та же ветка вниз)
L455-458:  (та же ветка вверх)
L516-519:  (та же ветка вверх)
```
Тот же приём в `FUN_CODE_822c` **L606–609**.
Кросс-проверка: `ROM 0x8148 INC R3 / 0x8149 CJNE R3,#08h,814Eh / 0x814C MOV R3,#00h`.

**CONFIRMED: ровно 8 знакомест, мультиплексирование по кругу.**

### 2.3 Таблицы знакогенератора в ПЗУ (адреса посчитаны из дампа, байты — из HEX)

| Выражение в дампе | Реальный адрес | Байты | Где |
| --- | --- | --- | --- |
| `*(byte *)((ushort)(param_3 + 0x1c) + 0x824a)` | **`0x8266 + digit`** (`0x824A + 0x1C`) | `41 49 48 4C 44 46 42 43` | **L460** (`FUN_CODE_8135`), **L611** (`FUN_CODE_822c`) |
| `*(byte *)((ushort)(param_3 + 0x89) + 0x817a)` | **`0x8203 + digit`** (`0x817A + 0x89`) | `41 49 48 4C 44 46 42 43` | **L483** (`FUN_CODE_8135`) |
| `*(byte *)((ushort)(param_3 + 0xac) + 0x8157)` | **`0x8203 + digit`** (`0x8157 + 0xAC`) | `41 49 48 4C 44 46 42 43` | **L521** (`FUN_CODE_8135`) |

Все три выражения указывают на **одни и те же 8 байт**; два из них дают
адрес `0x8203`, третий — `0x8266`, где лежат те же байты.
Кросс-проверка инструкциями: `ROM 0x8154 ADD A,#ACh / 0x8156 MOVC A,@A+PC`
(PC=0x8157) и `ROM 0x8177 ADD A,#89h / 0x8179 MOVC A,@A+PC` (PC=0x817A).

> **Поправка к `docs/hardware_from_pseudocode.md` — исправлено.** Там было
> записано `0x824A - 0x1C = 0x822E`; арифметика должна быть сложением:
> база = **`0x8266`** (см. таблицу). По адресу `0x822E` лежит хвост соседней
> таблицы `0x8224`.

### 2.4 Десятичная точка — старший бит

```c
L460-461:  FUN_CODE_810f(*(byte *)((ushort)(param_3 + 0x1c) + 0x824a) |
                         *(byte *)CONCAT11(0xa1,param_1) & 0x80);
L520-522:  pbVar4 = (byte *)(CONCAT11(0xa1, *(byte *)CONCAT11(0xa1,param_1)) & 0xff80);
           bVar3 = *(byte *)((ushort)(param_3 + 0xac) + 0x8157) | (byte)pbVar4;
L611-612:  (то же самое в FUN_CODE_822c)
```
**CONFIRMED**: к байту знакогенератора примешивается бит 7 ранее записанного
байта (`& 0x80`), а при read-modify-write адрес обрезается маской `0xff80`.
Значение бита — **HYPOTHESIS**: десятичная точка либо признак «знакоместо
погашено».

### 2.5 Гашение знакоместа

```c
L474:  FUN_CODE_810f(0, param_3);      // в ветви останова развёртки
```
**CONFIRMED**: запись `0` = пусто → индикация активного уровня «1 на сегмент»
(уровень — HYPOTHESIS, сам факт «0 = пусто» — CONFIRMED).

### 2.6 Развёртка на таймере 1

`FUN_CODE_8135` — обработчик, перезагружающий `TL1`/`TH1`:

| Строка | Константы | Перезагрузка | Период, тактов |
| --- | --- | --- | --- |
| **L396–397** | `TL1 = 0xf9; TH1 = 0xfd;` | `0xFDF9` | 519 |
| **L445–446** | `TL1 = 0x2d; TH1 = 0xdc;` | `0xDC2D` | 9 171 (режим мигания) |
| **L503–504** | `TL1 = 0xd9; TH1 = 0xfe;` | `0xFED9` | 295 |
| **L572–573** | `TL1 = 0xa4; TH1 = 0xfc;` | `0xFCA4` | 860 |
| **L534–535** | `TL1 = DAT_CODE_829a; TH1 = DAT_CODE_8299;` | `ROM[0x829A]/ROM[0x8299]` = `65/FC` → `0xFC65` | 923 |
| **L441–442** | таблица из ПЗУ | см. ниже | переменный |

```c
L441: TL1 = *(undefined1 *)((ushort)((param_5 << 1 | param_5 >> 7) + 0x74) + 0x8224);
L442: TH1 = *(undefined1 *)((ushort)((param_5 << 1 | param_5 >> 7) + 0x6c) + 0x822b);
```
Кросс-проверка: `ROM 0x821F MOV A,R5 / 0x8220 RL A / 0x8221 ADD A,#74h /
0x8223 MOVC A,@A+PC` (PC = `0x8224`) и `0x8226…0x822A MOVC A,@A+PC`
(PC = `0x822B`); далее `0x8224 MOV TL1,A` и `0x822B MOV TH1,A`.

Байты таблицы пар `(TH1, TL1)` по базам `0x8297`/`0x8298`:

```
0x8297: 01 E2 | FC 65 | FC 53 | FC 3F | FC 2B | FC 17 | FC 03 | FB EF | FB DB | ...
        k=0    k=1    k=2    k=3    k=4    k=5    k=6    k=7
```
`k=1` даёт `0xFC65` = 923 такта — ровно то значение, которое код подставляет
через `DAT_CODE_8299`/`DAT_CODE_829A` (**L7–8** — объявления, **L534–535** —
чтение). Дальше лесенка периодов растёт на 20 тактов: 923, 941, 961, 981,
1001, 1021, 1041.

Останов развёртки — **L471–473**:

```c
bVar3 = TCON;  TCON = bVar3 & 0x3f;   // сброс бит TR1/TF1/…
ET1 = 0;                               // запрет прерывания от таймера 1
```

### 3.3 Чего в этой половине ПЗУ нет

* **HYPOTHESIS**: сама матрица клавиатуры сканируется в недостающей половине —
  оттуда уходят `func_0x67ba` (43 вызова), `func_0x57ae` (24), `func_0x575f`

## 4. Принтер и обмен с медленной периферией

Прямых строк «printer» в дампе нет — **привязка конкретных адресов к принтеру
это HYPOTHESIS**. Что CONFIRMED:

### 4.1 Рукопожатие через `0x0C7A`

```c
L1950:  param_1 = &DAT_EXTMEM_0c7a;
L1956:  cVar5 = (DAT_EXTMEM_0c7a < 0xa5) << 7;
L1957:  if (DAT_EXTMEM_0c7a != 0xa5) break;
L1958:  DAT_EXTMEM_0c7a = 0x7a;
```
(`thunk_FUN_CODE_d398`; повторения: **L2765–2773** в `FUN_CODE_d398`,
**L2362/L2717** в `FUN_CODE_d381`.)

**CONFIRMED**: канал «ждём `0xA5` → отвечаем `0x7A`» — типичный обмен с
медленным партнёром.

### 4.2 Парный ящик `0x00FE`/`0x00FF`

```c
L2303:  puVar13 = &DAT_EXTMEM_00fe;
L2306:  *puVar13 = 0xa5;
L2307:  puVar13[1] = 0x5a;
L2308:  puVar13 = &DAT_EXTMEM_0c7a;
```
(`thunk_FUN_CODE_d398`; читается в **L2355–2361**, **L2712**, **L3118**.)

**CONFIRMED**: та же магия `A5/5A`, затем переход ожидания на `0x0C7A`.

### 4.3 Статусные флаги

* `0x00D3` — **ждут `0x5A`** (`FUN_CODE_fb91` **L12632–12633**,
  `FUN_CODE_fb95` **L13065–13066**), сбрасывают в `0` (б274/б282/б469).
* `0x0107 = 0xFF` (`FUN_CODE_ba2a` **L1461**), дальше код его не пишет.
* `0x00BC = BANK3_R7` (`FUN_CODE_fb91` **L12702**, `FUN_CODE_fb95` **L13135**).
* `0x0093 = 0` / `0x0094 = 1` — всегда вместе (**L934–935, L1052–1053,
  L1234–1235**).

### 4.4 Write-only латч `0x81xx`

* **L398–399**: `pbVar4 = (byte *)CONCAT11(0x81,param_1); *pbVar4 = 0;`
* **L499–501**: `pbVar4 = (byte *)CONCAT11(0x81,(char)pbVar4);
  *pbVar4 = bVar3; T0 = 1;` (значение `bVar3 = 0x55`, **L497**)

Окно нигде не читается → `recover/hal.py` помечает его `"w"` и по умолчанию
запрещает чтение. Кросс-проверка: `ROM 0x81F3 MOV DPH,#81h / 0x81F6 MOVX
@DPTR,A / 0x81F7 SETB P3.4`.

**HYPOTHESIS** (по `recover/hal.py:243-249`): страница `0x81` — принтерный
путь, потому что рядом `ROM 0x81E7: MOV DPL,#31h` (смещение `0x31`
соответствует `CONCAT11(param_6 + 'i', 0x31)` в **L509**).

## 5. ППИ (8255) — что дамп действительно доказывает

CONFIRMED (только это):

* по смещениям `0x0009` и `0x000B` пишутся ровно две константы: **`0x89`** и
  **`0xA9`**, отличающиеся одним битом (бит 5), под условием `_7_4`
  (**L850–852, L968–970, L1109–1111, L1138–1155**);
* ни один **портовый** регистр такой микросхемы в дампе не трогается — обращений
  к смещениям `0x000A`/`0x000C` нет вообще.

HYPOTHESIS (явно помечена такой в `recover/hal.py:32-37` и в
`decode_8255_control`): `0x89`/`0xA9` — слова управления 8255, тогда ППИ
сидит на смещениях `0x0000..0x0003`. HAL моделирует ровно то, что доказано —
два write-латча — и отдаёт декодер `0x89`/`0xA9` **только** для диагностики.

Кросс-проверка байтами (`ROM 0xB2A9`, функция `FUN_CODE_b274 @0xB274`):

```
B2A9: MOV    R1,#0Bh
B2AB: MOV    A,#89h
B2AD: JNB    27h.4,B2B2h      <- условие _7_4 из дампа (бит 0x27.4 = byte 0x27 bit 4)
B2B0: MOV    A,#0A9h
B2B2: MOVX   @R1,A
```
Совпадает с **L850–852** дословно, включая имя условия `_7_4`.

## 8. Чего в этой половине ПЗУ нет

1. **Инициализация** — `LJMP 0x0A06` в векторе сброса уходит в `0x0000..0x7FFF`.
2. **Сканирование клавиатуры** — страница `0x91` (`ROM 0x8393`) не покрыта
   ни одной функцией дампа; виден только вход `P1.3` «есть нажатие».
3. **Драйвер принтера** — нет ни одной строки, прямо называющей принтер;
   есть общий механизм медленного обмена (§4).
4. **692 из 756 вызовов `func_0xNNNN`** уходят в недостающую половину; самые
   частые — `func_0x67ba` (43), `func_0x57ae` (24), `func_0x575f` (21),
   `func_0x1d65` (18), `func_0x57c9`/`func_0x57d1` (18/15),
   `func_0x7241`/`func_0x725c`/`func_0x7276`/`func_0x728c` (по 15–16).

Поэтому структура кассы, которую подтверждает этот дамп: **8-знаковый
мультиплексный дисплей на странице `0xA1xx` + отдельный write-only латч
`0x81xx`, опрос клавиши по `P1.3`, развёртка на таймере 1 с таблицами
перезагрузок в ПЗУ, канал рукопожатия `0x0C7A`/`0x00FE` со статусом `0x00D3`,
два управляющих байта `0x89`/`0xA9` на смещениях `0x0009`/`0x000B`, — и ни
одного полного драйвера выше этого уровня.**

Остальное — `docs/hardware_from_pseudocode.md` (разбор по блокам),
`docs/firmware_recovery.md` (что из этого вообще исполняется) и таблица
`EVIDENCE` в `recover/hal.py:117-298` (адрес → свидетельство в машиночитаемом
виде).
